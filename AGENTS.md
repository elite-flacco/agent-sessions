## Relay architecture

- `src/collector/adapters/` contains provider-specific JSONL normalization. Adapters must never return raw prompts, responses, reasoning, credentials, or tool arguments. Session hierarchy is normalized into `parent_external_id`, `session_kind`, `agent_label`, and `agent_depth`: Codex uses `session_meta.parent_thread_id`, Claude sidechains use `agentId` as the child identity and `sessionId` as the parent, and Zcode uses `session.parent_id`/`task_type`. Titles prefer provider-authored metadata: Codex reads `threads.title` from `~/.codex/state_5.sqlite` through `src/lib/codex-db.ts`; Claude prefers the latest `custom-title`, then latest `ai-title`; both fall back to the first meaningful user message, and Codex subagents (whose task prompt is encrypted inter-agent payload) fall back to a title derived from the spawn's `agent_path`. The collector reconciles Codex database titles after every full scan because renames do not change rollout JSONL. `CODEX_STATE_DB_PATH` is the Codex test seam and `__resetCodexDbCache` clears connections between tests. The Zcode adapter resolves authoritative titles and missing `cwd`/`repository` values from Zcode's own session database (`~/.zcode/cli/db/db.sqlite`, opened read-only via `src/lib/zcode-db.ts`); after file scans the collector reconciles Zcode metadata and status from the database's message/part tables, including database-only sessions and unresolved `AskUserQuestion` tools. `ZCODE_DB_PATH` is the Zcode test seam and `__resetZcodeDbCache` clears connections between tests. Branch stays JSONL-derived because Zcode's schema has no git field.
- Session status preserves provider evidence: explicit completion markers produce `completed`, explicit abort/cancel markers produce `interrupted`, and an unresolved Zcode `AskUserQuestion` tool produces `needs_attention` (displayed as "Awaiting input") — reserved solely for a session waiting on the user. Genuine failures produce `failed` and carry a `StatusReason` (`usage_limit`, `insufficient_balance`, `network_error`, `model_error`, `execution_error`) surfaced as "Failed · <reason>"; the reason is classified from the terminal Zcode error text in `zcodeStoredStatus` (`src/collector/index.ts`), and the rollout-only `status: "failed"` path (`src/collector/adapters/zcode.ts`) defaults to `execution_error`. Reasons attach only to `failed` and travel through the nullable `status_reason` column and `NormalizedSession.statusReason`; `staleStatus` and `terminalStatus` pass a `{ status, reason? }` `TerminalStatus`. `needs_attention`, `failed`, `interrupted`, and `completed` are terminal; unterminated sessions are `running` for 10 minutes after their last update and then read as `incomplete`; inactivity alone must never imply interruption. Attention views (`getAttentionSessions`, the `attention` filter, failure counts) span `interrupted` + `needs_attention` + `failed`. Overview includes attention sessions updated today or during the previous two local calendar days.
- `src/collector/index.ts` owns idempotent source fingerprinting, persistence, and filesystem watching. Full scans and the watcher hold durable leases (`src/collector/lock.ts`, `collector_leases` table) so two processes never ingest concurrently; concurrent in-process syncs share one run. Per-adapter scan state lives in `adapter_scans`.
- `src/db/` owns the versioned SQLite/Drizzle schema; generated migrations live in `drizzle/`. Schema changes must update both `src/db/schema.ts` and the bootstrap SQL in `src/db/client.ts`, then run `npm run db:generate`. `src/db/migrate.ts` establishes a migration baseline for databases created by the original bootstrap SQL before applying newer migrations.
- `src/lib/queries.ts` is the server-side read boundary for dashboard data. It imports the SQLite client, so client components may import **types only** from it; runtime values shared with client code belong in `src/lib/types.ts`, `src/lib/labels.ts`, or `src/lib/format.ts`. Session status is derived at query time (`running` goes stale to `incomplete` after 10 minutes without updates) — do not trust the stored status column for presentation. `getInsights()` derives cache-effectiveness and cost-outlier signals for the `/insights` page under the same pricing-trust rule.
- Detailed transcripts are never persisted. `sessions.source_path` links normalized metadata back to its original JSONL file, and `src/lib/transcript.ts` reads supported user/assistant messages and tool arguments/results on demand for `/sessions/[id]`; Zcode sessions instead prefer Zcode's read-only `message`/`part` tables so deleted rollout files and event-only subagent JSONL remain readable. Keep common credential redaction in that boundary, exclude raw reasoning records, and do not pass `sourcePath` into client-side list views.
- Usage and cost: adapters emit normalized per-model usage (`ModelUsage`: uncached input, output, cache read/write, optional provider-reported cost) persisted in `session_model_usage`. Dollar costs are never stored — `src/lib/queries.ts` derives them at read time from `src/lib/pricing.ts`, a checked-in, client-safe pricing table with per-model rates, effective dates, and source URLs. A session gets a dollar figure only when every usage row is priced (reported or table match); otherwise it reads "unavailable" and is excluded from dollar aggregates. Per-session cost is **rolled up over the subagent subtree**: `getSessionsCostUsd` expands each id through a provider-scoped recursive CTE on `parent_external_id` so a main session's figure is its own spend plus every descendant subagent's, and the pricing-trust rule spans the subtree (one unpriced descendant row makes the whole roll-up unavailable). `getSessionUsage` returns own spend (`costUsd`/`costSource`, and `models`) alongside `subagentCostUsd` and `totalCostUsd`/`totalCostSource` so the detail view shows the split. Totals must keep visiting sessions individually — `getUsageSummary`, the overview cost card, and the insights week total count every session once, because rolling up there would double-count subagents, which are already rows of their own. Per-session _rankings_ do roll up: the insights cost outliers credit each usage row to its topmost ancestor **within the week window** (`rootIdOf` in `getInsights`), so a delegating main session is listed once with its whole tree's spend, its subagents never appear as separate outliers, and the roll-ups still sum to exactly `weekTotalUsd` — which keeps the Pareto and top-5 shares bounded even when a subtree straddles the window edge. `usdPerMin` there measures the tree's cost against the main session's wall clock, since subagents run inside it. Keep new pricing entries dated and sourced.
- Pages: `/` Overview (`overview-view.tsx`; patterns via `getOverviewPatterns()` — activity heatmap, session-length histogram, week cost-at-a-glance), `/sessions` combined Sessions/Projects browser (`dashboard.tsx`) with server-side throttled ingestion on each 15-second refresh and subagents nested beneath main sessions, `/sessions/[id]` full transcript detail plus parent/child navigation (`session-detail.tsx`), `/usage` (`usage-view.tsx`), and `/insights` (`insights-view.tsx`; `getInsights()` — URL-backed 7/30-day skill and MCP rankings, active-installed-but-unused capabilities with coverage-aware conclusions, cache hit rate and $-saved derivation, plus cost-outlier Pareto/$-per-minute signals). The Capability adoption card (`capability-usage-card.tsx`) is one pane at a time: a headline adoption ratio, a segmented bar whose widths are the tab counts, then `capabilityTab` tabs for Skills / MCPs / Unused / By provider (URL-backed, client-side — every pane's data ships with the card, so switching never refetches). Only the first three feed the segmented bar and carry counts; **By provider** is a second view of the same usage, not a fourth bucket, and it re-sorts `used` across both kinds because the query hands it back grouped by kind. Its cells shade per provider from `CapabilityInsight.byProvider` on a **log** scale — usage spans three orders of magnitude against a ramp with a handful of steps, so linear shading would paint every row but one the same shade — and a provider whose coverage is not `complete` and observed nothing gets a hatched cell, because Relay cannot distinguish "never called it" from "never saw the session". The two usage tabs render a ranked ladder scaled against **that tab's own peak**, because a skill invocation is a workflow and an MCP invocation is a single tool call — one shared scale flattens the skills ladder against far larger MCP counts. Bars reuse the quantized `meter-fill-N` classes. The coverage caveat renders inside the Unused pane only, since it qualifies the unused conclusion and nothing else. `/projects` redirects to `/sessions?view=projects`. All primary pages share `src/components/sidebar.tsx`; browsing filters are URL-backed and polling uses `router.refresh()`.
- Global agent setup inventory lives under `src/lib/agent-inventory/` and is read live by `/agents`; it never enters SQLite or the session collector. Provider readers must stay allowlist-based: return names, enabled/install status, packaging, provenance, repositories, safe paths, warnings, and global instruction Markdown, but never MCP commands/arguments/env, credentials, or raw config. **Exception:** scheduled-task readers (`discoverXxxScheduledTasks`) additionally surface each task's instruction body verbatim (Codex `prompt` from `~/.codex/automations/`, Zcode `script_path` contents, Claude `SKILL.md` body) because that prose is the task's purpose and the user authored it. This is a deliberate, user-accepted tradeoff: a secret pasted into a prompt will render on `/agents`. Do not extend this exception to other capability kinds. Skills are deduplicated by canonical source and distinguish personal links, skills.sh lockfile installs, plugin contributions, built-ins, and unknown sources. User-authored MCP servers from each provider's config (`~/.zcode/cli/config.json` `mcp.servers`, `~/.claude.json` `mcpServers`, Codex `mcp_servers.*` tables) are tagged `origin: "personal"` so they render with the "Personal" badge rather than "Unknown". The Zcode reader also walks `~/.zcode/cli/plugins/cache/<marketplace>/<plugin>/<version>/` via `discoverCachePlugins` to surface cache-only marketplace plugins the Zcode UI lists but `installed_plugins.json` doesn't record; cache-only plugins read as `status: "installed"` (enabled state unknown) unless they appear in `enabledPlugins`. The public discovery API takes an explicit `{ kind: "global" }` scope so future project-level discovery can reuse the model and Inventory/Compare UI without weakening the current global boundary. Comparison assessments derive from all four normalized inventories and never alter discovery or configuration. Status semantics: absence from a provider's enabled-plugins map is an unknown state and reads as `installed` — only an explicit `false` reads as `disabled`; Codex `[[skills.config]]` entries (`name = "<plugin-short-name>:<skill>"`, bare name for standalone skills) override individual skill status on top of the plugin state; a plugin whose install path is missing on disk (or a broken skill symlink) reads as `unavailable`. Disabled capabilities are retained in inventories (never filtered at the discovery boundary) so comparison can distinguish deliberate disables from missing installs; only the Compare view renders them — the Inventory list and summary counts hide disabled entries. The Inventory view shows one provider at a time (the summary cards are a single-select provider control, defaulting to the first) and selects capability Kind from a vertical rail on the left (`agent-kind-rail-layout` / `agent-kind-rail` in `agent-setup-view.tsx`), so only one kind's pane renders at a time; the Kind the rail owns is excluded from `matchesCapability` via its `ignoreKind` flag, while Status and search still filter. Each pane nests capabilities as collapsible Source groups (by origin — Personal / Marketplace / skills.sh / Built-in, open by default, carrying the origin badge), with the existing repo/plugin skill sub-group nested beneath; the origin badge is stated once per source group rather than on every row. Instructions ride as a fourth rail entry whenever the provider ships an instruction file, and that entry never disappears in response to the selected Kind or Status — the rail owns Kind, so hiding the entry would strand the user with no way back to it; whether the instruction matches the active search/status only decides whether it can stand in as a result when no capability matches. The Compare view is unaffected and stays a flat table. Compare has no provider dimension at all: `parseAgentSetupFilters` drops `provider` when `view=compare`, so the matrix always spans every provider (narrowing to one would hide exactly the missing-from-that-provider rows drift analysis exists to surface) and the summary cards there link into that provider's Inventory instead of filtering the matrix. Skills carry a whitespace-normalized `contentFingerprint` of their SKILL.md (instruction files likewise fingerprint normalized content); drift assessment treats `enabled`/`installed` as one "active" state, compares skill content instead of packaging, and computes discrepancies over the three primary providers only (Pi is contextual). Drift splits by cause: when status/origin/packaging agree everywhere and only the SKILL.md fingerprint differs the row reads `content_drift`; a genuine status/origin/packaging mismatch reads `configuration_drift`. Missing-from-one-provider is a Fix only for skills.sh-origin capabilities and a Review otherwise. The Needs Attention view renders assessment messages on Fix rows only — Review rows get their reason from their section heading and their specifics from the provider cells — and splits Reviews into one section per reason (`reviewSections` in `agent-setup-view.tsx`, ordered most-actionable first) while Fixes stay a single section; empty reasons render no heading. Discovery emits `stale` warnings for multi-version plugin caches and skills.sh lockfile entries with no installed skill; the Needs Attention view surfaces deduplicated warnings and per-provider duplicate installs (`findComparisonDuplicates`, identical-content vs shadowing). The `/agents` page has three URL-backed tabs — Inventory, Compare, and Scheduled tasks; the third live-reads per-provider scheduled/recurring jobs (Codex automations, Claude scheduled-tasks dirs, Zcode `workflow_definition` rows, Pi none) under the same allowlist exception, and renders all discovered tasks in a single schedule-first table sorted by cadence (active daily → weekly → monthly → other, inactive last) where each row is a native `<details name="agent-tasks">` exclusive accordion revealing model, target project, source path, and the verbatim instruction body. Scheduled-task scans list only subdirectories (`readDirectoryEntries(dir, { directoriesOnly: true })`) because providers keep bookkeeping files beside task directories — Codex's `~/.codex/automations/.run-jitter-salt` — and appending a task filename to one yields ENOTDIR, which would read as an unreadable-config warning. The Codex reader resolves each automation's `target.project_id` against the `local-projects` map in `~/.codex/.codex-global-state.json` (ids and names only) into `targetProjectName`; an id that map does not contain gets an `orphaned` task warning, rendered as a "Target missing" flag on the row summary plus the reason inside the accordion. That state is the same mismatch that makes Codex's own editor report the task as nonexistent, and it is only judged when the map was readable — an unreadable state file leaves every target unresolved rather than orphaned.
- New UI must use semantic tokens and component classes from `src/app/globals.css`; do not introduce raw Tailwind palette colors, arbitrary values, inline styles, or `dark:` variants. For dynamic chart fills, use the quantized `meter-fill-N`/`spark-fill-N`/`heat-fill-N` classes instead of inline styles.

## Plan authoring rules

When a task requires an implementation plan, include `docs/superpowers/plan-dod.md` in the planning context. The final plan task must review and update `README.md` for user-facing behavior and `AGENTS.md` for architecture or convention changes. Never weaken the Definition of Done to fit a smaller task; skip a formal plan when the work does not need one.

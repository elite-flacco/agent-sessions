## Capability usage insights

`session_capability_usage` is the privacy-safe normalized boundary for observed skill and MCP usage. Claude and Zcode use native `Skill` calls, Codex and Pi require exact live-inventory matches for `SKILL.md` reads, and namespaced MCP calls roll up to server names through exact, collision-free aliases derived from active inventory metadata. Relay stores only session/provider identity, capability kind and canonical name, a stable event identifier, and a valid provider timestamp — never prompts, arguments, results, contents, credentials, or raw configuration. Extraction changes must increment `NORMALIZATION_VERSION` so a full collection backfills unchanged sources. `getInsights(range, inventories)` combines persisted observations with live active inventory and provider coverage; its shared `OverviewRange` (`7d`, `30d`, or cutoff-free `all`) controls cache, cost, and capability windows together, while `capabilityTab` controls only the visible capability tab. Providers with incomplete coverage are excluded from unused conclusions. It returns every observed capability in `used` (the card, not the query, decides how many rows to show), each carrying a `byProvider` split of invocations — the aggregate query groups by provider, and folding it is exact because a session belongs to exactly one provider, so per-provider distinct session counts never overlap — plus `installedCount`/`installedUsedCount`, the adoption denominator and numerator counted over distinct active installations under complete coverage only — both stay `0` when no provider qualifies, and the card then states a bare used count instead of a ratio it cannot support. `used` and `unused` may name the same capability, because unused status is judged per provider installation; only the `installed*` counts are a strict subset relation, which is why the headline ratio is built from those and not from the tab counts. Zcode is complete only when `adapter_scans.capability_reconciliation_complete` records a successful latest pass across the required `session`, `message`, `part`, and `tool_usage` queries; failures preserve prior rollout evidence until a later successful pass. Plugin activity remains outside this feature.
